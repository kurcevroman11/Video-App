# Этап 7 — продуктовые фичи, детальная спецификация

Четыре фичи ниже независимы друг от друга — можно отдавать агенту по одной, а не все сразу целиком, тем более что у них разная сложность (чат — тривиален, запись — сопоставима по сложности с самим Этапом 5).

---

## 1. Чат в комнате

### Где хранится

Новая таблица в БД `room-service` (не отдельный сервис — объём и характер данных не оправдывает выделения):

```prisma
model RoomMessage {
  id        String   @id @default(uuid())
  roomId    String
  userId    String
  content   String
  createdAt DateTime @default(now())

  room      Room     @relation(fields: [roomId], references: [id])
}
```

### Поток данных

Реалтайм-доставка — через `signaling-service` (WS), персистентность — через gRPC-вызов к `room-service`. Это то же разделение ответственности, что и везде в проекте: `signaling-service` не хранит бизнес-данные сам.

```
Client: chat:send { content } ──▶ signaling-service
                                       │
                                       ├─ validate: длина, rate limit (см. ниже)
                                       ├─ room-service.SaveMessage(roomId, userId, content)  [gRPC]
                                       └─ broadcast всем в комнате: chat:message { userId, content, createdAt }
```

**Почему персистентность через gRPC-вызов, а не просто broadcast без сохранения:** без сохранения история чата пропадает при переподключении/входе нового участника — это ломает ожидания пользователя от любого чата. Загрузка истории — отдельный REST-эндпоинт через `gateway-service` → `room-service.GetMessages(roomId, cursor?)`, курсорная пагинация, а не "отдать всё сразу" (история может расти неограниченно).

### Правила, которые нужно заложить сразу

- Лимит длины сообщения (например, 2000 символов) — валидация на `signaling-service` до вызова `room-service`, не полагаться только на ограничение БД
- Rate limiting на отправку (например, не больше 5 сообщений за 10 секунд с одного `userId`) — защита от флуда в реалтайм-канале, где обычный HTTP-throttling `gateway-service` не участвует вообще
- Экранирование/санитизация содержимого — на клиенте при рендере (никогда не вставлять `content` как raw HTML), но это стоит явно прописать агенту, а не полагаться, что он сам вспомнит про XSS в чате

## 2. Демонстрация экрана

### Механизм

Технически — просто ещё один `Producer` в уже существующей SFU-модели Этапа 5, с одним нюансом: нужно различать на клиенте камеру и demo экрана, чтобы отрисовать их по-разному (обычно демо экрана — крупно, камера — маленьким тайлом).

```typescript
const screenStream = await navigator.mediaDevices.getDisplayMedia({ video: true });
const track = screenStream.getVideoTracks()[0];

const producer = await sendTransport.produce({
  track,
  appData: { source: 'screen' }, // ключевое отличие от appData: { source: 'camera' }
});
```

`appData` долетает до остальных участников внутри события `new-producer` (расширяем payload из Этапа 5 полем `source`), и клиент рендерит producer типа `screen` иначе, чем `camera`.

### Бизнес-правило: сколько демонстраций одновременно

Решение для MVP: **одна демонстрация экрана на комнату одновременно**. Технически mediasoup спокойно потянет несколько параллельных screen-share Producer'ов, но с UX-точки зрения несколько одновременных демонстраций экрана в одном звонке — это путаница, а не фича. Проверка — на уровне `signaling-service` (хранит `activeScreenSharer: userId | null` в состоянии комнаты рядом с остальным in-memory/Redis-состоянием из Этапа 6): если кто-то пытается начать демо, пока активна чужая — сервер отклоняет с понятной ошибкой, а не молча позволяет второй поток.

### Остановка демонстрации — обязательно обработать нативную кнопку браузера

Пользователь может остановить демо не через UI приложения, а через нативную кнопку "Stop sharing" в браузере — это должно быть поймано:

```typescript
track.onended = () => {
  // сработает и на явный клик "Остановить показ" в приложении, и на нативную кнопку браузера
  socket.emit('stop-screen-share', { producerId });
};
```

Без этого обработчика: пользователь жмёт браузерную кнопку "Stop sharing", локально поток обрывается, но сервер и остальные участники ничего не узнают — на экранах у всех останется замороженный последний кадр демонстрации.

## 5. Тест-кейсы по всем четырём фичам

**Чат**
- сообщение сохраняется в БД и доставляется всем в комнате в реальном времени
- сообщение длиннее лимита — отклоняется до сохранения
- превышение rate limit — отклоняется с понятной ошибкой, не молча дропается

**Демонстрация экрана**
- второй участник, пытающийся начать демо при уже активной чужой — получает отказ
- нативная кнопка "Stop sharing" браузера корректно закрывает producer на сервере
- после остановки демо остальные участники получают `producer-closed` для этого потока

## 6. Что сознательно НЕ входит в этот этап

- Единый смикшированный файл записи со всеми участниками в сетке — отдельная фича поверх раздельной записи
- Транскрипция/субтитры записи — не блокирует Definition of Done
- Совместное редактирование экрана (аннотации поверх демонстрации) — за рамками MVP видеозвонков
- Автоматическое масштабирование `recording-service` под много одновременных записей — актуально для Этапа 8
